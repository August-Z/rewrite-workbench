# 竞品基线与差异验证

本文用于约束产品定位、验收与公开表述。项目定位为：**把一次手工修改变成一条看得懂、可验证、能重复执行的全项目改写。**

本轮资料核对日期：2026-09-09。以下能力来自官方文档和官方仓库；**尚未完成竞品操作实验，没有完成时间、准确率或性能测量数据。** 文档没有提及某项能力，不等于产品没有该能力。开始实验时需要记录实际版本、可用功能及文档差异。

## 要验证的产品差异

这里记录的是假设，不是已经成立的优势。**M2 只评估两项预设操作：用户选择操作，从现有代码节点预填字段并确认条件，查看候选解释与补丁。** M2 可以保存 fixtures 以验证预期结果，但不会根据 before/after 或正反例自动推导、收敛规则；相关能力归入 M4 后续研究。

| 假设 | 可观察的产品行为 | 验证方式 | 不成立时的调整 |
| --- | --- | --- | --- |
| H1（M4 后续）：before/after 能帮助推广一次修改 | 根据示例提出规则候选，由用户显式确认固定值、变量和适用范围 | 对照完成同一任务的时间、求助次数、规则编辑次数 | 保留 M2 的预设操作与字段确认，不实现自动归纳 |
| H2（M4 后续）：正反例能降低规则收敛成本 | 根据用户标注的“应修改”“不应修改”提出条件调整，并说明理由 | 测量正确完成任务前的迭代次数，以及新反例加入后的结果 | 保留 M2 的 fixture 保存和显式条件编辑，不自动调整规则 |
| H3：来源约束更容易被理解和核验 | 显示声明/导入证据、别名关系与无法解析的原因 | 使用同名符号、alias、shadowing、未解析模块 fixture 对照 | 对无法证明的情况 skip；不得将名称相同当成来源相同 |
| H4：本地项目内的连续流程减少操作负担 | 从打开项目到匹配、审阅、导出补丁在一个连续流程内完成 | 与 ast-grep VS Code 和 Codemod 本地路径比较热任务与首次接入 | 若收益只在展示层，优先做更小的集成或插件 |

Rust 用于解析、索引、匹配和确定性补丁等适合的层；是否获得性能优势需测量。项目不会以“用了 Rust”替代任务收益，也不会自建完整 TypeScript 类型检查器作为早期前提。

## 同 fixture 公平对照协议

### 任务与参考结果

M1 起建立公开、合成的小型 TSX fixture 集合；通过独立人工检查确定每一处的预期结果。M2 起在案例可获取时加入获得许可、可公开复现的真实改写案例；缺少外部案例不阻止内部 alpha。M2 对照只测试两项预设操作与显式条件确认，不测试尚未实现的 H1/H2。不能只挑选最适合本项目的任务。

首轮至少覆盖以下三个层次：

1. **结构层任务**：已明确指定的一类 TSX 属性替换，包含空白、注释、多行和嵌套结构；用于比较最基本搜索、变量捕获、预览与应用。
2. **来源层任务**：只改来自指定包与导出的组件，覆盖直接导入、导入别名、本地同名组件、另一个包的同名组件、局部遮蔽。只有进入版本支持范围的解析路径才计入自动改写承诺。
3. **边界层任务**：spread、动态表达式、重复属性、无法解析的模块、未支持的 re-export 路径、语法错误。预先声明哪些允许修改、哪些应保持、哪些必须报告未知。

每个任务发布：初始文件快照、准确的自然语言要求、必须修改位置、禁止修改位置、允许 skip 的未知位置、最终期望补丁。不能将所有难例划入 unknown 来获得好看的零误改结果。

测试变体分为学习集与保留集。操作者可用学习集构建规则；保留集在规则冻结后执行，避免只记住示例。来源层案例不能靠仅匹配组件名称完成；普通文本搜索/替换也应作为简单任务的对照。

### 选择最好的对照，而不是最弱的对照

- 每个任务选取能够完成它的最强可用竞品路径，不要求同一竞品赢得所有任务。
- Codemod 可使用 Studio 加 CLI/JSSG 的完整路径；ast-grep 可使用官方扩展与 CLI；WebStorm 可使用官方模板、modifiers 和文档。
- 将“不支持”“未找到可用操作”“实验故障”“准确完成但较慢”分开记录。不支持某项任务，不等于引擎在其声明范围内发生误改。
- 给竞品操作者合理的练习机会，保存最终配置与步骤。工具熟练者先建立有效基线，再单独观察普通开发者；不把本项目作者与首次使用竞品的人直接作性能或效率对比。
- 若允许 AI 帮助生成规则，两边采用相同的可用模型、时间和调用预算；另行报告无需 AI 的受限任务结果。AI 起草和确定性执行不能混为一项正确性证据。
- 所有比较固定代码、依赖、系统、硬件、网络条件与版本。记录失败与中止，不仅发布成功案例。

### 分开测量首次接入和重复任务

| 测量 | 起止范围 | 需要记录 |
| --- | --- | --- |
| 安装冷启动 | 从干净环境取得工具，到首次成功执行相同 fixture | 下载、安装、账号、CLI/PATH、索引与配置时间；网络及缓存条件 |
| 项目首次打开 | 工具已安装，从新 fixture 项目到可开始操作 | 项目发现、索引、语言选择、必要配置 |
| 热任务 | 项目已准备，从收到新要求到提交正确补丁 | 主动操作时间、等待时间、总历时、求助与迭代次数 |
| 引擎执行 | 输入、规则和索引状态固定，从执行到结果 | 冷/热索引分别报告；样本规模、峰值内存、重复次数与分布 |
| 二次修改 | 为已有 fixture 加入一个明确反例，用户显式修改条件，到正确补丁 | 条件修改成本、结果回归、是否需要重写脚本；M2 不自动收敛规则 |

安装耗时不能被描述成匹配引擎性能；单次最佳耗时不能替代多次分布。小仓库有足够交互速度时，优先优化正确完成任务的成本。

### 正确性和覆盖率

**no-miswrite 是公开 fixture 上的硬门槛，不能宣传为任意项目安全保证。** 这里的 miswrite 包括改动禁止位置、结果不符预期、补丁触及无关字节或应用覆盖了较新的文件内容。

- **必须改写命中率**：正确修改的必须位置 / 全部必须位置。
- **误改数**：禁止位置或无关范围被改写的次数；展示绝对数和受测分母。
- **unknown skip**：无法在当前能力内确认的位置与原因。不得静默漏掉或给出虚假的“安全”结论。
- **已知位置误 skip**：支持范围内本应完成但未完成的位置；不能与合理 unknown 合并。
- **补丁完整性**：在隔离 fixture 副本应用，验证目标输出、未受影响文件及注释/格式边界；保存补丁与校验结果。
- **陈旧预览**：预览后修改源文件，再尝试应用；必须检测来源版本不一致，要求重新计算，不能覆盖新内容。

普通开发者试用采用等价任务、交叉顺序；分别报告有无既往经验。用户试用结果用于判断可用性，fixture 测试用于判断所测输入的正确性，二者不能互相替代。

## 记录模板

每次运行至少记录：`run_id`、日期、工具/版本、操作者熟练度、fixture 版本、任务类型、AI 使用方式、冷/热状态、总历时、主动操作时间、等待时间、求助次数、规则迭代次数、必须位置命中、误改、合理 skip、已知位置误 skip、最终补丁、复现说明。

数据集状态与数值字段在真实运行前保持未测；不填演示数字。结果报告同时附上失败案例和范围限制。

## 与研发里程碑的关系

| 里程碑 | 本文对应交付 |
| --- | --- |
| M0 规划 | 冻结首批任务、差异假设、指标与竞品对照路径 |
| M1 正确性底座 | fixture、参考补丁、误改/未知分类、可重复测试入口 |
| M2 完整本地 alpha | 完成两项预设操作、节点字段预填与条件确认、候选解释、patch 和 fixture 保存的垂直路径，并进行内部实操；竞品/外部研究未开展时如实标注 |
| M3 公开 v0.1 | 公布已测范围、可复现结果与限制；公开宣称优于竞品和扩大推广之前取得实际对照证据 |
| M4 受证据驱动扩张 | 根据任务收益与真实使用选择更多改写类型、来源解析、集成，以及 H1/H2 后续研究 |

研发不以预先找到固定人数的访谈对象、外部参与者或完成一条竞品实测为前提。没有这些数据时标注“未开展”，继续完成内部 alpha；实际对照证据用于支持优于竞品的公开主张和扩大推广，真实使用证据用于决定扩张范围。发布与增长判断见 [launch-validation.md](./launch-validation.md)。
