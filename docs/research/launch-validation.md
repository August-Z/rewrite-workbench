# 发布与增长验证

本项目将 GitHub Star 作为重要的传播目标，同时要求关注来自真实开发者对公开成果的认可。**计划不保证任何 Star 数量，也不将技术实现完成等同于传播成功。**

本文是待执行方案：尚未运行竞品对照、外部试用或发布活动，没有转化率、任务耗时或增长测量数据。所有门槛都是预先提出的项目决策规则，不是行业基准或预测模型。

## 研发先完成垂直路径

M2 从“打开本地 TSX 项目 → 选择两项预设操作之一 → 从现有节点预填字段并确认条件 → 解释候选与来源 → 审阅补丁 → 检查文件版本 → 应用或导出”开始，并支持保存 fixtures。before/after 自动识别和正反例自动收敛属于 M4 后续假设，不在 M2 实现范围。竞品实测与外部参与者都不是工程 alpha 的硬前置。

| 阶段 | 必须产出 | 证据作用 |
| --- | --- | --- |
| M0 规划 | 支持范围、fixture 方案、竞争假设与发布材料清单 | 避免对外承诺未定义能力 |
| M1 正确性底座 | 确定性结果、unknown skip、文件版本校验、可重复 fixture 验证 | 判断支持范围内是否适合继续集成 |
| M2 完整本地 alpha | 两项预设操作的完整可用路径、fixture 保存、真实内部操作记录；竞品/外部研究未开展时如实标注 | 验证工程流程，形成可展示版本；不据此宣称新手优势或胜过竞品 |
| M3 公开 v0.1 | 可安装发行物、独立安装复现、透明限制、诚实演示和反馈入口 | 收集真实使用、传播和失败反馈 |
| M4 受证据驱动扩张 | 选择经证实的下一种任务、集成，或 before/after 与正反例推导研究，复查正确性与维护成本 | 避免为追热度堆砌不稳定功能 |

若竞品实测或外部试用尚未开展，标注“未开展”，继续内部验证和范围内研发；完成质量检查后可以开展有限公开试用。公开宣称优于竞品和扩大推广需要实际对照证据，功能扩张还需真实任务证据；不能以固定访谈人数或至少一条竞品实测把 alpha 开发挂起。

## v0.1 的公开表达

首版用一个能够真实完成的故事介绍产品：

> 在一个 TSX 项目中修改指定来源组件的一类属性，检查哪些位置会变、哪些因来源不同被排除，再生成可审阅补丁。

具体语法、来源形式和操作，以发行版实际支持为准。README 必须同时包含：

- 一个 20–40 秒可理解的真实操作演示，说明录制版本和 fixture；剪辑不得隐藏关键配置、人工修正或失败。
- 可复制的安装与示例命令；没有账号或 API Key 的路径只能在确实存在时宣传。
- 明确的支持矩阵、未知跳过规则、已知限制、恢复/重新计算流程。
- 与最强可用竞品的具体任务比较；数据不足时只展示功能差异和实验计划。
- 合成 fixture 与期望补丁，让别人可以重现同一个结果。
- 简短的 issue 模板，收集版本、最小输入、期望结果、实际结果；提醒不要提交私有源码或凭据。
- 清楚说明所复用的开源引擎及其许可证，避免让用户误认为底层能力全部自研。

可将“原始代码、匹配解释、生成补丁、应用后的代码”做成四段连续示例。截图和短片吸引首次关注，成功处理用户自己的任务才是后续传播基础。

## 公平对照与对外披露

按 [competitive-baseline.md](./competitive-baseline.md) 执行相同 fixture、相同要求和最佳竞品路径。冷安装、项目首次索引、热任务、引擎运行分别统计。熟练者基线和新用户试用分别报告。

传播材料只使用实际测得且可复现的数据。不得从一个小 fixture 推导“快几十倍处理所有仓库”；不得把拒绝处理大量输入包装为零误改优势；不得拿竞品首次安装时间与本项目缓存后的引擎耗时比较。

公开结果应包含失败、已知位置误 skip、未知输入比例和版本。有限 fixture 上零误改不等于所有项目语义安全。若后来发现已发布比较不准确，修正原始材料并在对应发布说明中解释。

## 真实传播路径

### 首轮渠道

1. **项目主页与演示页**：英文 README 提供直接入口，中文说明补充背景；首屏只讲一个任务收益。
2. **现有开发者社区**：围绕可复现案例发布技术说明，遵守各社区的自我推广规则；避免把相同内容机械铺到大量无关渠道。
3. **前端维护者与内容创作者**：公开发布后接受自愿试用，用真正发生的案例完善说明。合作、赞助或付费展示需要披露。
4. **上游生态**：说明与 ast-grep/Oxc 等工具的关系，分享可复现实现经验与限制。不得在无关 issue/PR 中插入推广。
5. **迭代发布**：围绕一项可验证改善发布，例如处理新的导入形式、缩短首次正确补丁时间；不把版本号变化本身包装成重大进展。

联系、发帖、提交 issue 或 PR 应由项目维护者明确授权后执行。此文只定义方案，不代表已进行任何对外操作。

### 明确禁止的增长方式

- 购买、交换、机器人批量或多账号 Star。
- 把正常使用、下载或错误修复与点 Star 绑定。
- 以奖励诱导无实际兴趣的 Star，或声称不存在的用户、客户、口碑。
- 隐瞒付费分发，把广告流量当自然增长。
- 从私有仓库抽取源码、截图或数据作为宣传素材。
- 在 CLI 中默认采集代码、文件路径或细粒度行为来追踪转化。

可以在 README 中简短邀请“觉得有帮助可以 Star”，但不反复打断产品操作。

## 指标与归因边界

| 层次 | 指标 | 能回答的问题 | 不能直接推导的结论 |
| --- | --- | --- | --- |
| 曝光 | 发布页/帖子展示或查看数据 | 有多少人可能看到了内容 | 独立目标用户数、真实阅读与认可 |
| 兴趣 | 演示页访问、示例启动、指向 GitHub 的点击 | 哪种内容产生进一步了解行为 | 点开 GitHub 后是否 Star |
| 使用 | 自愿反馈、成功跑通的安装记录、复现案例、再次使用 | 是否解决实际任务 | npm 下载量等于独立活跃用户 |
| GitHub | 同期仓库访问、referrer、Star 总量变化 | 关注度与时间走势 | 某一渠道或某次点击造成了某一颗 Star |
| 质量 | 误改、安装失败、已知位置误 skip、issue 复现率 | 推广是否带来可承受的产品质量压力 | 没有收到 issue 就没有问题 |

同一观测窗口记录：起止时间、发行版本、发布渠道、可用曝光数、演示访问、GitHub 跳转点击、Star 起止值、净变化、外部事件、数据缺失。净增 Star 为结束总量减去开始总量；它可能包含新增和取消。

**曝光、GitHub 点击和同期净增 Star 不能精确关联到同一批用户。** 用户可能跨设备、延迟访问、从其他分享发现项目或先 Star 后试用。多渠道同期发布还存在重复触达。若展示“净增 Star / GitHub 点击”等窗口比值，必须称为混合窗口观察值，不称为用户转化率，也不归功于单个渠道。

可给演示页不同公开链接添加简单的活动标识，仅用于聚合来源分析。不得通过隐藏指纹或追踪个人 Star 行为弥补归因缺口。没有足够数据时写“无法判断”，不估造精确数字。

## 预设门槛与行动

以下初始门槛用于作出可审查的决定。执行前记录采用版本；若调整，写明原因，不能事后改门槛把不理想结果解释为成功。

### 质量门槛

- **M1 → M2**：支持矩阵内的固定 fixture 必须完成全部必要改写，禁止位置无误改；未知位置有明确 skip；陈旧预览不会覆盖较新文件。
- **M2 工程 alpha**：通过支持范围内的内部检查，完成两项预设操作到补丁的完整路径；不要求先获得竞品实测或外部操作者。缺失研究标注“未开展”，不宣称已验证新手可用性或竞品优势。
- **M2 → 有限公开试用**：在两份独立、干净的项目副本上完成安装到补丁的垂直路径，可以由内部人员执行。未参与实现的人按文档独立复现作为后续研究目标；尚未完成时明确披露，不伪造独立验证。
- **M3 广泛推广与竞品优势主张**：发布版的必需检查通过，安装说明与展示一致，并取得相同任务、最佳竞品路径的实际对照证据。只有结果支持时才宣称相应优势；缺少证据时维持有限试用和内部研发。已知可能造成误改的问题必须先修复或收窄支持范围，不因推广日历跳过。

出现确认误改、覆盖较新内容等问题时，立即暂停对受影响能力的宣传和扩张，修复并重跑相关场景。与问题无关的研发可以继续；无需重新验证所有已经保持有效的结果。

### 任务价值门槛

M2/M3 阶段逐步积累 6 位普通前端开发者的试用，作为初始可用性样本目标，**不是开工或继续研发的前提**。建议观察：

- 至少 4/6 人在没有维护者逐步指导的情况下完成支持范围内任务。
- 正确完成热任务的中位时间较最佳可用竞品减少至少 30%；若现有工具已非常快，可用明显降低配置/迭代负担替代，但需单独证明并解释。
- 至少 3 人主动带来第二个实际场景或在之后再次使用；口头称赞不能替代重复行为。

样本很小，只足以决定下一步实验，不足以声称普遍优势。如果没有明显任务收益，先调整入口、交互或支持范围；不要仅凭发布时收到 Star 就扩大技术面。

### 传播门槛

首轮以两个不同来源的定向发布窗口为观察单位，每个窗口建议观察 7–14 天，并单独记录同时发生的版本发布或外部推荐。下列是诊断规则：

- **曝光不足**：没有足够、可解释的目标开发者触达，先改演示、标题、渠道和安装入口。此时不能断言产品没人需要。
- **看过但没有继续了解**：在累计至少约 200 次可识别的目标演示页访问后，GitHub 跳转与示例启动仍很少，优先调整价值表达。访问来源质量不明时不套用该门槛。
- **愿意点击但无法成功使用**：有仓库访问和安装尝试，失败反馈集中在接入或规则理解，优先修复产品路径；扩大分发只会放大问题。
- **愿意使用但 Star 少**：先观察用户是否认为项目值得收藏、README 是否说明维护方向，以及正常 Star 邀请是否清楚。不要添加强制或奖励机制。
- **Star 增长但无任务证据**：维持当前范围，继续收集真实案例。短期话题传播不能替代 M4 的扩张依据。

因各平台曝光口径、链接漏报和窗口混杂，暂不设虚假的通用“Star 转化率”。每轮保留原始汇总值与限制，比较相近渠道、相同观察长度和类似版本阶段的变化。

### M4 扩张条件

一次只增加一个新的改写类型、来源解析能力或集成方向。优先候选应同时具备：

1. 至少 3 个彼此独立的实际场景请求，而非同一组织的重复描述。
2. 现有垂直路径已有可复现收益，且正确性问题可控。
3. 能补齐明确的 fixture 与未知边界，维护成本符合当前团队能力。
4. 用户有持续使用或分享迹象，传播增量并非只来自单次不相关热点。

证据不足时继续打磨当前路径、接受小范围实验，或调整定位；不预先承诺全语言、完整类型系统、全自动迁移和万人 Star 目标的达成时间。

## 发布后记录

每轮留下一个简短记录：发布了什么、给谁看、触达如何测量、多少人成功完成任务、出现哪些问题、同期 Star 如何变化、哪些归因无法判断、下一轮只改哪一件事。未测字段写未测，所有公开数字保留版本和时间范围。
